# Workflow model

Flowcordia treats a workflow as one governed object with several connected representations.

## One identity

| Representation | Purpose |
| :-- | :-- |
| Canvas | Human-readable visual composition |
| Canonical document | Deterministic workflow definition |
| Generated source | Executable task code derived from the model |
| Git commit | Immutable reviewed version |
| Deployment | Runtime artifact built from a commit |
| Run | Execution tied to a deployment version |

The workflow ID remains stable across these representations. A visual edit does not create a separate workflow from the code under review.

## Canonical document

The canonical document records nodes, edges, configuration, function references, credential references, and workflow metadata in a deterministic format. Equivalent workflow states should compile to equivalent generated output.

Some Studio nodes are implemented through pinned Activepieces pieces. For those nodes, Flowcordia preserves the piece name, piece version, selected operation, inputs, and property settings required to reconstruct the visual step. The upstream builder remains the editing surface; the Flowcordia workflow document remains the governed contract.

## Durable wait contract

Waits use one canonical `control.wait` operation with two configurations:

- `duration` with `durationSeconds`
- `until` with an ISO `untilTimestamp`

Studio can represent those modes as Delay For and Delay Until. The runtime compiler maps the canonical contract to Trigger.dev `wait.for(...)` or `wait.until(...)` without changing the workflow identity.

## Round-trip fidelity

A visual/source round-trip must preserve the meaning of the node, not merely its position on the canvas. For Activepieces-backed nodes this includes the pinned piece settings and the credential references attached to that specific node.

If Flowcordia cannot reconstruct an upstream piece without losing required information, the conversion should fail instead of silently producing a different workflow.

## Exact-version rule

A changed commit is a changed executable version. If the proposal head moves after a preview deployment was built, Flowcordia must not silently execute the older deployment as though it represented the new head.

## Fail closed

When identity cannot be proven across proposal, deployment, and run, execution should stop with a clear explanation. Running a convenient but stale version would break the governance model.

## Why this matters

The connected identity makes review, rollback, audit, debugging, and collaboration possible without forcing visual builders and developers into separate systems.
