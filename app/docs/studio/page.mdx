# Studio

Studio is the visual working surface for a repository-backed workflow. It helps builders compose the flow while preserving the contracts developers expect from code.

The current Studio is hosted on the upstream Activepieces builder. Flowcordia owns the workflow model, runtime contracts, bridge, and product shell around that builder rather than maintaining a separate fork of the visual editor.

## What the canvas represents

A canvas contains nodes, connections, configuration, and stable identifiers. It is a view of the canonical workflow model—not an independent export format.

Typical nodes include:

- Event and schedule triggers
- Conditions, loops, and branches
- HTTP and data transformations
- Repository-owned TypeScript Source steps
- Durable waits
- Math, Text, Date, and Store helpers

See [Essential nodes](/docs/essential-nodes) for the current wait and helper contracts.

## Flowcordia Studio shell

Flowcordia applies its own light, monochrome Studio treatment to the embedded builder: white canvas and panels, black primary actions, and neutral borders and controls.

The branding layer does not replace the upstream builder implementation. External integration and piece logos keep their original colors so the services being used remain easy to recognize.

## Durable waits

The Wait node supports two explicit modes:

- **Delay For** pauses for a non-negative duration.
- **Delay Until** pauses until a valid date and time.

Both round-trip through Studio as the pinned Activepieces Delay piece. At runtime Flowcordia compiles them to Trigger.dev's durable `wait.for` and `wait.until` primitives.

## Editor and Source

Switching between Editor and Source should not rebuild the visual surface just because the view changed. The mounted builder state is preserved while Source is active, then restored when the user returns to Editor.

Activepieces-backed node settings are also preserved during the visual/Source round-trip. A helper or integration should come back with the same operation, inputs, piece version, and node-level credential references it had before the switch.

## Durable drafts

Visual changes are stored as durable draft operations. A browser refresh or temporary interruption should not silently discard the current working state.

The draft remains separate from production until it is published through the Git proposal lifecycle.

## Bounded visual editing

Flowcordia only renders structures it can represent accurately. Unsupported code remains visible as code instead of being flattened into a misleading graph.

This boundary matters because convenience should never weaken review, ownership, or runtime correctness.

## Structural preview

Before publishing, Studio can validate the workflow shape and show the generated source that corresponds to the current model. Live execution requires a deployment built from the exact version being reviewed.
